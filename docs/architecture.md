# Архитектура

## Обзор связки

Проект собирает существующие инструменты в локальный RAG-стек поверх Obsidian-vault:

```
┌─────────────────────────────────────────────────────────────────┐
│  Obsidian vault (.md)                                           │
│  ГОСТы · регламенты · внутренние инструкции                     │
└──────────────┬──────────────────────────────────────────────────┘
               │ scan (чанкинг по заголовкам, вложения .md)
               ▼
┌─────────────────────────────────────────────────────────────────┐
│  mdrack — SQLite                                                │
│  ├─ chunks / sections / files  — структура vault                │
│  ├─ chunks_fts (FTS5)          — полнотекстовый индекс          │
│  ├─ vec_chunks                 — векторный индекс               │
│  └─ гибрид: RRF (k=60) объединяет FTS и векторные выдачи       │
└──────────────┬───────────────────────────────┬──────────────────┘
               │ MCP (stdio)                   │ embed / query
               ▼                               ▼
┌──────────────────────────┐     ┌──────────────────────────────┐
│  opencode (AI-агент)     │     │  LM Studio (localhost:1234)  │
│  инструменты mdrack_*    │     │  qwen3-embedding + LLM       │
│  ищет чанки, читает,    │     └──────────────┬───────────────┘
│  отвечает инженеру       │                    │
└──────────────────────────┘                    │
                                                ▼
                              ┌──────────────────────────────────┐
                              │  hayhooks (MCP, localhost:1417)  │
                              │  ask_notes: поиск → PromptBuilder│
                              │  («только из документов») → LLM  │
                              └──────────────────────────────────┘
```

## Потоки данных

### Индексация
1. `mdrack scan --root <vault>` обходит vault, парсит markdown (заголовки → секции, секции → чанки 900–5000 символов с оверлапом).
2. Текст чанков прогоняется через LM Studio (`/v1/embeddings`), вектора пишутся в SQLite.
3. Полный текст попадает в FTS5-таблицу.
4. Повторный `scan --changed` обрабатывает только изменённые файлы (детектор изменений по mtime/хэшу).

### Поиск
- **text** — FTS5 по запросу;
- **semantic** — запрос → эмбеддинг → kNN по `vec_chunks`;
- **hybrid** (по умолчанию) — обе выдачи объединяются Reciprocal Rank Fusion.

### Ответ агента
1. Инженер спрашивает агента (opencode).
2. Агент вызывает `mdrack_search` / `mdrack_read_chunk` — получает цитаты с ID.
3. Ответ строится на основе цитат; проверяемость — через `read_chunk`.

### ask_notes (план)
Фиксированный промпт («только из найденных документов») + LLM — один инструмент, возвращающий готовый ответ, без интерпретации агентом.

## Технологии

| Слой | Выбор | Почему |
|---|---|---|
| Хранилище | SQLite (FTS5 + свои вектора) | ноль сервисов, один файл, переносимо |
| Эмбеддинги | LM Studio, qwen3-embedding-0.6b | локально, OpenAI-совместимый API |
| Поиск | BM25 (FTS5) + вектор + RRF | гибрид устойчивее каждого слоя в отдельности |
| Транспорт | MCP (stdio / streamable HTTP) | стандартный способ дать инструменты агенту |
| Пайплайны | Haystack + hayhooks | готовые блоки (сплиттеры, промпты, LLM) без самописного кода |
